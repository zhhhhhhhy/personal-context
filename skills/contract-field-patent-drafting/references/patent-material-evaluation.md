# 专利材料评估协议

本协议用于回答“这套专利材料是否完整、是否适合交给律师、距离正式提交还差什么”。它是内部交接工具，不是国家知识产权局评分表，也不是授权概率预测。

## 1. 先确定评价对象和结论类型

评价开始前先记录：

| 评价对象 | 必须确认的内容 |
| --- | --- |
| 技术来源 | 最新正文、可编辑源文件、图表源、实验或工程记录 |
| 专利材料 | 说明书、权利要求书、摘要、附图、可编辑文件和 PDF |
| 实现证据 | 代码、配置、日志、脱敏样例或可复现步骤；没有就标为未知 |
| 著录项目 | 申请人、发明人、权属、优先权、最早公开时间和联系方式 |
| 现有技术 | 申请日前专利、论文、产品或公开网页；未检索不能假定新颖性 |

先选择评价目标：

- **律师交底初稿**：检查技术方案、支撑关系、证据边界和文件可读性，允许著录项目和现有技术检索存在待办。
- **代理师撰写准备稿**：除上述内容外，要求权利要求支撑矩阵、实现证据和检索方向已经可交接。
- **正式提交准备稿**：还必须有完整著录项目、正式附图审查、申请日前检索和代理师最终确认。不能只凭内部评分得出这个结论。

## 2. 给每条信息标记证据等级

对技术特征、实验数字和著录项目分别标记来源，不把“写进文档”当成“已经被证明”。

| 标记 | 含义 | 可以支持的用途 |
| --- | --- | --- |
| `S` | 最新正文或其他权威技术源直接写明 | 技术方案、实施例和说明书支撑 |
| `I` | 真实代码、配置、日志或脱敏运行记录支持 | 可实施性和实现细节 |
| `O` | 学校、申请人、代理师或正式文件确认 | 著录项目、权属、公开时间线 |
| `P` | 合理的可选实施方式，尚未由材料直接证明 | 说明书候选内容；不能直接写成已验证效果 |
| `M` | 模型辅助参考、自动评价或局部人工试审 | 受限的实施例和诊断结果，不能叫完整人工金标准 |
| `U` | 未知、待补或无法定位来源 | 必须列为开放事项，不能默认为事实 |
| `X` | 与权威来源冲突或明显不受支撑 | 需要删除、改写或暂停结论 |

独立权利要求的必要限定原则上应有 `S` 或 `I` 支撑；申请人、发明人、权属和公开时间线原则上应有 `O` 支撑；`P`、`M`、`U` 不得伪装成已确认事实。

## 3. 按固定顺序评估

### 步骤一：版本和来源审计

建立来源登记表，至少记录路径、修改时间、哈希或页数、用途和排除项。确认：

1. 哪个文件是当前技术依据；
2. 哪些旧版本明确排除；
3. 早期简版只提供了哪些工程骨架；
4. 参考专利只承担哪些结构和版式作用；
5. 关键数字能否回到章节、表格、日志或脚本。

来源不能闭合时，先标为开放事项，不用文档格式分数掩盖。

### 步骤二：写出一条“问题—手段—结果”链

用三句话检查技术方案是否完整：

1. **问题**：现有处理在什么技术环节失败，例如证据不足仍写入、必要内容遗漏或引用不能支持输出；
2. **手段**：系统接收什么技术数据，执行哪些可操作的处理，在哪个条件下分流、写入或复核；
3. **结果**：产生什么可观察的技术结果，例如阻止错误写入、保留来源定位、形成可回放记录。

如果只能写“提高准确率、实现智能填写、减少人工”，而不能说明输入、处理和控制动作，技术性和可实施性不得判满分。

### 步骤三：拆出独立权利要求的技术链

把独立权利要求拆成以下六类限定：

1. 技术对象和输入数据；
2. 数据组织或预处理；
3. 核心判断、计算或门控；
4. 结构化输出；
5. 写入、阻断、修正或复核动作；
6. 审计、回放或其他可观察结果。

对合同字段方案，通常要核对“合同文档/字段任务—字段规范—固定证据包—必要信息项—前置充分性判断—候选值和引用—联合核验—写入或复核—审计记录”是否闭合。缺少输入、核心处理或结果中的一环，就不能把独立权利要求判为完整。

### 步骤四：建立权利要求支撑矩阵

每一条权利要求、每个必要限定都建立一行：

| 字段 | 需要填写的内容 |
| --- | --- |
| 权利要求号 | 例如 1、2 或 13 |
| 限定 | 用短句拆出一个技术动作或结果 |
| 说明书位置 | 技术方案步骤、实施例或系统实施方式 |
| 原始来源 | 正文章节、页码、表格、代码或配置 |
| 证据标记 | `S`、`I`、`O`、`P`、`M`、`U` 或 `X` |
| 结论 | 支持、部分支持、待补或冲突 |
| 补强动作 | 补段落、补代码证据、改写限定或删除 |

判定规则：

- 独立权利要求每个必要限定都必须有说明书解释和至少一个来源锚点；
- 从属权利要求新增的限定不能只出现在实验数字或标题中；
- 系统、设备和存储介质权利要求必须能映射回方法步骤；
- 只由 `M` 结果支持的实验现象不能变成独立权利要求必要限定；
- 找不到支撑位置的限定标为 `U` 或 `X`，不能用“本领域常规”自动补齐。

### 步骤五：检查可实施性和技术效果

分别回答四个问题：

1. 技术人员是否知道输入数据的格式和来源；
2. 技术人员是否知道每一步如何处理、分支条件是什么；
3. 技术人员是否知道输出如何影响写入、阻断或复核；
4. 技术效果是否由区别技术手段产生，而不是只重复目标。

模型名称、阈值、窗口大小、重试次数和接口格式只有在来源或实现证据支持时才写成必要限定；否则放入可选实施方式或待补项。

### 步骤六：检查证据边界和实验解释

把结果分成“直接来源事实、实现证据、可选实施方式、待验证事项”。重点检查：

- 模型辅助参考没有被称为人工金标准；
- 固定证据条件下的风险控制结果没有被扩大为所有合同、字段或模型的普遍提升；
- 生成质量、动作选择、修正循环和端到端产品性能分别解释；
- 未完成的人工审计、训练实验和系统测试仍列为开放事项；
- 实验规模用于实施例和验收边界，不反向限定独立权利要求。

### 步骤七：准备新颖性和创造性检索

这一步不直接下“有新颖性”或“可以授权”的结论，而是建立检索工作底稿：

1. 对权利要求 1 拆出特征组；
2. 对每篇最接近文献逐项记录“已公开、未见、待核读”；
3. 区分单篇文献是否完整公开与多篇文献的组合；
4. 记录区别特征对应的技术效果和可能的组合动机；
5. 写明公开日、申请日、优先权和法律状态是否已核实。

没有完成申请日前检索时，结论只能是“检索准备完成”或“待检索”，不能写成“新颖性通过”。

### 步骤八：检查表达、格式和著录项目

检查三类问题：

- **表达**：技术术语前后一致，少用项目日志词、内部实验代号和防御性长列表；用“固定证据条件下的评测”“评测设置”“核心评测集”等可读表述；
- **文件**：说明书、权利要求书、摘要、附图、PDF 和可编辑源互相对应，编号、引用和图题一致；
- **著录项目**：申请人、发明人、地址、权属、优先权、最早公开日期和联系人分开核对，未知项高亮，不从 Word 作者属性或内部编号推断。

## 4. 评分方法

评分只用于管理交接进度。每个维度使用三档：

- **完整**：关键检查点都有来源和可复核输出，得该维度满分；
- **部分**：主链路成立，但存在可明确补强的缺口，得该维度一半分；
- **缺失/冲突**：核心内容无法定位、相互矛盾或没有形成可执行方案，得 0 分。

| 维度 | 权重 | 满分条件 |
| --- | ---: | --- |
| A 来源与证据链 | 15 | 当前版本、排除项、数字来源和材料用途均可追溯 |
| B 技术方案完整性 | 25 | 问题、输入、处理、输出、分支和审计形成闭环 |
| C 权利要求与说明书支撑 | 20 | 独立权利要求闭合、从属限定有支撑、矩阵可定位、术语一致 |
| D AI/软件技术性与可实施性 | 15 | 技术数据、具体处理、控制动作和技术效果相互对应 |
| E 新颖性/创造性准备 | 15 | 已完成申请日前检索、对比文件矩阵和区别特征分析 |
| F 正式申请与文档质量 | 10 | 文件齐全、摘要和附图合格、著录项目可核对、渲染无缺陷 |

总分为各维度得分之和。评分时必须同时记录证据和开放事项，不能只给一个数字。

## 5. 硬门槛和状态映射

### 5.1 律师交底硬门槛

以下项目任一失败，状态不能高于 `not_ready`：

1. 没有确定最新技术来源，或排除的旧材料被混入结论；
2. 独立权利要求缺少输入、核心处理或可观察结果；
3. 独立权利要求存在说明书完全没有支撑的必要限定；
4. 说明书只描述目标，没有足以实现主要流程的处理步骤；
5. 模型辅助标签、局部实验或推测事实被写成完整人工金标准或普遍效果；
6. 申请人、发明人或最早公开日期的未知状态被错误写成确定事实。

### 5.2 状态映射

| 状态 | 判定 |
| --- | --- |
| `not_ready` | 律师交底硬门槛失败，或总分低于 50 |
| `needs_supplement` | 硬门槛通过但总分为 50—69，先补技术方案或证据链 |
| `pass_with_open_items` | 硬门槛通过且总分为 70—84，可交律师继续修改 |
| `attorney_review_ready` | 硬门槛通过且总分为 85—100，可进入代理师深入撰写，但仍不等于可提交 |
| `ready_for_formal_filing` | 只有在著录项目、申请日前检索、正式附图和代理师最终确认均完成后使用 |

## 6. 必须输出的评估结果

评估报告至少包含：

1. 一句话结论和评价目标；
2. A—F 六个维度的得分、证据和扣分原因；
3. 律师交底硬门槛逐项结果；
4. 权利要求—说明书—原始来源支撑矩阵；
5. 未完成事项，每项写清“缺什么、放在哪、由谁确认、什么证据能关闭”；
6. 不能从本次材料推出的结论，例如新颖性、创造性、授权概率和完整人工金标准；
7. 可复现的文件校验、渲染和结构检查结果。

推荐的机器可读字段为：

```json
{
  "evaluation_target": "lawyer_handoff_draft",
  "total_score": 0,
  "status": "pass_with_open_items",
  "hard_gates": {},
  "dimensions": {},
  "claim_support_matrix": "path/to/matrix.md",
  "open_items": [],
  "limitations": []
}
```

结构检查脚本只能证明文件、编号和摘要等机械条件；不能替代来源审计、权利要求支撑、可实施性判断或现有技术检索。
