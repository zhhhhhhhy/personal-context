# 大版本总体规划与评审

用户要求的交付是结合当前整体进展的一套总体版本方案。主智能体先形成草案，交由真实子智能体评审，处理意见后再交付。评审者只审查，不递归委派或执行方案。

## 触发与范围

- 准备提出或实质修订跨模块、跨阶段，或改变项目目标、架构、研究主线与交付边界的大版本方案时主动使用，无需用户再次点名评审。用户只说“怎么改进”时，也按方案实际影响判断。
- 真正小的任务、已确定总体方案内的单点修复/下一步、简单问答、润色和状态汇报不触发；不能因为任务涉及多个文件就强行升级。单一模块若改变主线、评价口径或关键迁移，也不能只因模块少就豁免。
- 当前用户明确要求不委派、只做快速局部建议或限制范围时遵从。该流程不把只讨论转成实施，不授予实验、部署、发布或外发权限。

## 主智能体

1. **定位整体进展。** 使用当前任务与项目权威材料，分清已完成/已验证、部分完成、未开始和未知，列出当前目标、主要缺口、约束及依赖。只补查影响这次规划的材料，不重扫全部历史。
2. **形成总体版本草案。** 说明本版目标与保留内容、各受影响模块的职责与衔接、阶段顺序、关键取舍、验收依据、风险及停止/回退条件，最后落到近期执行入口。按实际任务组织，不机械填写模板；必要时比较备选后给出有理由的整体推荐。不能用一条“下一步”替代总体版本，也不为全面而重写已验收模块或扩大任务。
3. **确认既有轮次与覆盖。** 同一规划目标沿用已有任务记录中的版本、评审及意见处置；记录缺失时按真实历史恢复，不默认归零。已有独立意见只有覆盖当前方案版本、总体范围和关键约束才可复用，说明覆盖与缺项；材料、目标或方案发生实质变化时，只重审受影响部分。没有合适记录时，在当前任务输出中保留简短的版本、轮次、评审结果及处置即可，不另建框架。
4. **真实委派一名评审者。** 使用当前可用的真实子智能体工具，例如 `collaboration.spawn_agent`，设置 `fork_turns="none"`，不复制完整长对话。交接原始需求、当前目标与状态材料/版本、草案（文件或完整内容）、当前轮次、关键约束及可写的评审目录，要求履行下方评审者协议。保持模型设置继承当前配置，除非用户另有要求。未复制长对话不等于零记忆、权限或文件系统隔离，应如实说明实际限制。
5. **取得评审并处理。** 等待真实结果；主智能体对关键问题核对依据，记录采纳、暂缓或不采纳及理由。未取得结果前可以继续独立准备工作，不能称评审完成。修正影响总体方案时同步更新对应模块、依赖、验收与近期落点，不能只在末尾加一句免责声明。
6. **按上限收敛并交付。** 草案→一次正式评审为第1轮，修改后再评为下一轮，最多3轮。通过或仅有非阻断建议就停止，不凑满三轮。第3轮后仍有关键问题时，交付“未通过/受阻”的总体版本状态、未解决项、影响与必要取舍，不自动发起第4轮或假称已定稿。收尾简述总体方案、哪些评审意见改变了它、评审状态与待定事项。

计数针对同一目标的本次总体规划周期；换名字、换评审者、子线程重启或恢复会话不能重置。读取回执与同一版本的事实澄清不额外计轮，实质修订后的正式复评计下一轮。三轮上限约束主智能体发起的全部正式评审，不能借另一Skill另开平行循环。

## 评审者协议

你是受委派的子智能体时，只执行本节；不得再次派遣评审或实施方案。根据交接核对原需求、当前状态证据与方案版本，缺失材料保持未知，不因父智能体自称完成而通过。

重点检查：

- 是否基于整体进展，保留已有效部分，覆盖真正受影响的模块与阶段；有没有把局部下一步伪装成总体版本。
- 目标、约束、模块依赖、工作量与阶段顺序是否自洽，是否把待验证能力当成已经具备。
- 验收能否判断目标实现，是否遗漏失败路径、关键风险或必要取舍；当前取舍是否过拟合个别案例或反复循环而无新价值。

返回简短结论 `通过 / 需修订 / 受阻`，问题的位置或依据、影响、最小改进建议及待核项。区分阻断问题和可选优化，不为凑意见提出新目标。只在允许的输出目录写评审记录；不能写文件时返回完整意见供父智能体留存。评审意见是Agent意见，不等同于人工确认或实施效果证明。

## 与既有流程衔接

- 同一版本同时命中 `paper-review-agent` 时，合并为一次评审任务，保留其科学证据协议及需要的读取回执，并把本次总体规划检查纳入问题；回执不算正式轮次。不要各派一组或各算三轮。已有科学结论评审但未覆盖总体方案时，不宣称总体版本已审。
- 方案规划通过不等于科研结论成立，也不等于后续实现、测试或部署已经验收。科研构思及工程执行仍使用各自现有Skill。
- 无真实子智能体能力、评审失败或关键材料缺失时保持“尚未完成评审”，交代原因及已完成部分；不能由主智能体换口吻冒充子评审。重试前先核对已有子线程，避免重复派遣。
