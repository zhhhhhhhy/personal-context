# 渐进式 Context 加载与维护

## 日常加载

1. 每次会话只读一次四份核心文件；已经在上下文中就复用。由 `INDEX.md` 按任务目的选择个人偏好、论文、前端、后端或通用工作方法；明确指定的 Skill / Context 维护仍直达原入口，不递归加载目录。
2. 入口保留用途、触发条件、必要约束和下一层路由；细节、证据和旧版本只在需要时读取。信息不足或出现冲突时再深入，不整份重复返回已读文件。
3. 记忆从 `contexts/memory/INDEX.md` 关键词检索，再精确 `show`。项目资料先核对当前项目与版本，再用 `--project`；敏感材料仅在确需本人材料的任务中按需本地检索。
4. 条目正文在条目文件，registry 仅供脚本查询；不整份送入模型。合并、替代、归档和舍弃的旧内容退出默认检索，保留出处和去向。
5. 当前任务出现值得复用的信息时，按 `skills/personal-context/SKILL.md` 和 `docs/evolution/POLICY.md` 更新相关条目。没有新增价值时不写。旧候选、批量导入协议和实验报告不是日常必读。

领域页在现有按需层中承担任务分流：选主领域 → 匹配本次任务 → 读取相关经验/Skill → 出现版本、证据或案例疑点时再深入。每个领域页只提供指针和适用条件，不复制经验正文。普通任务不要求读完该领域的全部方法；项目事实只在当前任务需要时加载，跨项目经验也必须保留原范围与例外。

维持2026-10-23用户确认的粒度。需求、PRD、模块设计使用任务标签，Java、Go等使用技术标签或适用条件；不逐语言、逐阶段或逐项目增加必读层级。当前没有专属经验时如实使用已有通用方法和当前材料，不制造经验填满分类。

## 维护入口

保持短入口和明确路由；详细内容留在条目或参考文件，领域页不成为额外常驻层，也不建立第二套记忆库。修改后核对相关链接、必要边界和运行时副本，验证当前改动后停止。不要把字段校验或模型自查当作语义完整性证明。

`scripts/context-budget.py`、`scripts/context-meter.py` 和 `docs/context-loading/` 中的预算、测量记录保留为手动诊断资料，仅在用户明确请求相应诊断时使用。不在日常记忆维护或 Skill 同步前自动运行，不为了 token 下降删去有效内容或必要边界。既有阈值不在本次精简中调整。

批量提炼、来源包装和复核细则仅在用户明确要求历史导入时按专项入口读取；不自动计量工具返回、冻结样本或开启新一轮评测。
