| 阶段/模块 | 输入 → 产出 | 关键判断 |
|---|---|---|
| 问题凝练 | 当前论文目标、已有材料与具体失败 → 清楚的问题及应改善的行为 | 从材料出发，不预设复杂机制或把个别案例当作主导原因 |
| 多方案构造 | 问题、可借用的已有方法 → 多个有实质区别的技术路线 | 可以组合或改造算法，讲清各部分作用及具体新增，不反复包装同一个缺乏依据的方向 |
| 推荐前自评 | 候选、最接近的方法及具体案例 → 差异、必要性、证据缺口 | 用案例讲清实质改动和与简单方法的差别；未验证效果保持假设，不预设简单方法必然失败 |
| 比较与取舍 | 自评结果 → 可行性、工作量、风险、待验证点及有理由的推荐 | 以共同解决问题的科研合作者方式交付；让用户作当前需要的选择，不把所有候选都实施 |
| 选后拆分交付 | 用户选定的路线与当前授权 → 模块职责、输入输出、依赖、验证安排或大纲草图 | 构建或训练安排仍是计划；写入大纲不等于算法完成，构思本身不授权实验或论文修改 |

下次仅需构思时使用前三至四个阶段；已选定方案才进入对应拆分。已有研究定位或novelty条目仍按各自触发条件使用。需要论证复杂机制为何必要时，再读[具体检查方法](research.mechanism-necessity-check.md)。

## Boundaries

- 这是科研构思阶段的合作方式；固定范围的润色、审稿或状态查询不自动扩展成重新设计方案。
- 多个方案应有实质区别，数量按问题需要；当次三条路线不是固定配额。组合已有算法是可选手段，不要求每次拼接算法，也不把组合本身当作创新。
- 用户对当次联合选择方案的否定不等于禁止所有联合选择方法；应判断其针对当前问题的必要性与证据。
- 候选方案的可能效果、近邻差异与工作量在未核查或验证时保留待核状态；遵循既有优先发展但不强造novelty的边界。
- 本次方案一的选择、第三章内容与既有案例属于当次项目，不固化为通用路线；构思建议不授权启动实验、训练或修改论文。
- 这是本会话支持的构思到大纲交付片段，不是论文全生命周期；既有Skill提供的默认流程不在本条复制，未出现的阶段不补造。
