# 第三轮 Context 进化与实际加载比较

完成日期：2026-10-15（Asia/Shanghai）。最终效果由用户评估。

**新的渐进式规则在本轮减少了实际返回的 Context，但没有产生值得新增的长期规则。** 最终保留 3 项已有原则的补充证据、4 项待观察内容，拒绝 4 项过度泛化，新增 learned 规则 0 条。最值得继续观察的是人工补图时的位置、图像描述 Prompt 和图注交付。它只来自一个项目族，暂不成为默认规则。

## 材料与边界

本轮排除之前选用的 115 个父对话，重新固定 12 个未处理父对话：8 个用于提炼，4 个留出检查；覆盖学习、工程、文档和日常协作四类。训练实际对应 7 个独立项目或主题族，两份工业报告对话按同一家族计算。时间范围为 2026 年 4 月至 10 月，是按类别选择的历史样本，不代表完整一周或随机样本。

不少旧 JSONL 路径已经不存在，但本机应用仍能读取对应消息。因此仅对选中的对话使用原生 `read_thread` 恢复用户消息，保留原生线程、轮次及消息 ID；不把助手总结当原话。导出引用的行号指本机导出文件，不能宣称是旧 rollout 的原始行号。原始导出、脱敏证据、逐次读取日志和完整反思均留在忽略的 `.local/`，不提交 Git。

训练恢复了 28 条原生用户消息记录；经过已有提取、分类和去重，保留 26 条直接用户表达，另有 1 条复制方案的确认不进入偏好证据。26 条直接正文均未截断，合计约 899 tokens。许多消息只是短问句、继续指令或一次性操作，不能按对话标题推断稳定偏好。4 个留出对话仅用于反思冻结后的适用性检查，不补进本轮训练证据。

## 实际加载了多少

两名隔离分析代理分别执行渐进式和整表方式。双方先读取完全相同的核心与进化约束，再读完全相同的训练证据。渐进式读取候选索引、4 次有界检索和 3 条精确候选；整表方式读取旧版完整候选账本，脚本先验证其 46 条正文与当前分片记录相同。整表只是本次对照条件。

以下数值来自读取工具**实际返回的完整文本 payload**，包含 JSON 元数据与格式，采用 `o200k_base`；每次返回都计数，重复读取也会重复计入。本轮成功正文读取没有重读。

| 返回内容 | 渐进式 | 整表方式 | 说明 |
|---|---:|---:|---|
| 共同核心、路由、进化约束与 learned 入口 | 6,267 | 6,267 | bootstrap 内容与字节哈希一致 |
| 候选索引、检索结果及候选正文 | 2,861 | 7,690 | 候选读取本身减少 4,829，约 **62.8%** |
| 额外 Skill 与 Skill 目录 | 0 | 1,257 | 两方自行决定的补充读取，不能把差额全部归因于候选分片 |
| **Context 合计** | **9,128** | **15,214** | 实际返回的 Context 少 6,086，约 **40.0%** |
| 训练历史证据与引用元数据 | 3,060 | 3,060 | 内容与字节哈希一致；其中用户正文约 899 |
| **上述全部返回文本** | **12,188** | **18,274** | 约少 **33.3%**；不是整个实验成本 |
| 成功正文读取次数 | 10 | 6 | 渐进式文本更少，调用次数更多；未测延迟或费用 |

最直接可归于候选读取方式的差额是 4,829 tokens。若排除整表方额外的 Skill 读取，仅比较相同 bootstrap、证据和两种候选读取，合计为 12,188 对 17,017，约少 28.4%。四个常驻核心文件正文仍为 **1,823 tokens**，本轮没有扩大 Session 入口；6,267 是本次进化任务额外需要的约束与路由也加载后的返回量。

逐项保存的 16 个成功 payload 均通过 UTF-8 字节哈希、有效 JSON、字符数和 token 数复核；同时验证 bootstrap 与训练输入分别一致。脱敏序列化随后作了一处保留 JSON 结构的修复，全部 16 份既有 payload 在新实现下保持字节一致，未重跑或替换两组结果。另验证超额读取和越界路径会在返回正文、写成功日志之前拒绝。

这些数字**不包含**平台系统提示、工具 Schema、代理任务提示与输出、失败命令错误、主对话已有历史、资料恢复、人工整合及最终报告。主代理另一次训练读取返回 3,060 tokens，也没有计入上述任一分析方。整表方两次读取不存在或越界的工程 Skill，未获得正文，其报错开销不在成功 payload 账本内。无法据此声称整个会话 token、费用或延迟下降 40%。

## 本轮留下了什么

以下均为安全概括，不是历史原文。补强不改变待审候选状态，待观察不进入默认加载的 learned 规则。

| 处理 | 内容 | 范围与原因 |
|---|---|---|
| 补强 | 用户要求先规划复杂材料或实现任务时，交付指定计划文件 | 多次表达仍属于同一工业报告家族；只支持计划部分。沟通核心及候选 001/003/038 已覆盖 |
| 补强 | 遵循当次文件格式、名称和位置要求 | 题库和工业报告两个家族支持；属于已有交付职责，不推导默认桌面或 Markdown |
| 补强 | 技术文档具体且容易理解 | 只有一个家族；沟通核心已覆盖，不等于所有回答更长 |
| 待观察 | 手工补图时提供插入位置、图像描述 Prompt 和图注 | 明确且较有新意，但只有一个家族；与既有视觉检查候选有关，不是同一条要求 |
| 待观察 | 科研任务先寻找并安装相关 Skill | 当次请求与授权成立，缺少跨项目重复表达；不形成未来安装权限 |
| 待观察 | 清理磁盘时继续检查非缓存的大型占用 | 当次维护范围，设备与软件信息也可能过时 |
| 待观察 | 参考网站要求自行编写实现 | 一个任务中的实现约束，不等于所有开发禁用模板、组件和复用 |
| 拒绝 | 从历史删除选择继承未来自动删除权限 | 当前授权边界不能由历史操作改变 |
| 拒绝 | 将工具比较问句当作已确定的工具偏好 | 问题本身没有表达选择；标题和助手回答不能补证 |
| 拒绝 | 从一次慢对话推断长期速度优先、减少验证 | 没有表达这种取舍 |
| 拒绝 | 将某报告产品的 XML 与确认流程推广为所有文档的技术准则 | 这是项目设计，缺少跨任务表达及一般技术验证 |

完整脱敏决策见 [本轮决策记录](round-003-20261015.md)。实际应用结果为 0 条；`habits/learned.md` 内容和四个核心文件保持不变，`learned.json` 仅更新处理时间。

## 提炼质量是否足够好

**加载节省有实测支持；稳定偏好增量为零，观察覆盖仍需改进。** 两方都得出零晋升，说明当前证据门槛没有因为历史操作多而放松。但零晋升一致不能证明提炼结果完整，也不等于回答效果一样。

渐进式方分组为 9 项，整表方为 10 项；主代理按原话复核并统一范围后记录 11 项。分组口径不同，不能把这些数量当准确率或召回率。渐进式方遗漏了人工补图要求，而该原话已经完整返回给双方。因此本轮观察到的是一次提炼覆盖差异，**不能直接认定是分片检索造成漏证**。只有一对分析运行，也没有重复随机实验；整表方式同样不能被认定普遍更好。

可改进之处是：下一轮先在本机给每条直接用户表达记下“已形成观察 / 任务事实 / 非偏好 / 排除原因”，再做候选查重；结束前核对来源覆盖，避免有用的一次性要求在概括中消失。这是本轮发现的流程缺口，尚未通过新的独立批次证明修复效果，不回头调词重跑来改善本轮成绩。

最终反思在查看留出正文前固定哈希。四个留出情境分别涉及资料公开性、工具安装使用、文档篇幅和容量错误，检查后没有改动反思。它们没有覆盖人工补图，不能证明这一观察可泛化。由于没有晋升候选，本轮未另做“加规则 / 不加规则”的新回答盲测，**不宣称新 Context 提升了回答质量**。

本轮样本正文短、一次性要求多，是零新增的主要原因；逐条覆盖不足则是提炼流程自身的不足，两者应分开评价。当前结果适合保留资料、节省加载并继续观察；还不足以证明可以无人复核地自动丰富长期偏好。用户最终验收仍待评估。
