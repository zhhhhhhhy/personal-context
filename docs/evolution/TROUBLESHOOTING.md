# Context 进化：执行问题与解决记录

按症状查找本文件；它不属于常驻入口。记录观察到的问题、处理方法、验证证据和剩余边界。原始日志及私密值只保存在 `.local/context-evolution/`。

## T01：正文读到了，提炼结果却遗漏具体要求

- 发现：第三轮渐进式结果遗漏人工补图的具体交付要求；两方读取的训练 payload 哈希相同，原话未截断，因此不能归咎于没有检索到原文。
- 原因判断：已确认的是语义观察覆盖不足。直接概括主题、过早考虑晋升资格或注意力遗漏都可能导致这一现象；本轮没有证据确定唯一原因。
- 处理：先逐条建立来源、具体要求与观察的对应关系，再查旧候选；有价值的单次要求进入待观察层。脚本阻止漏消息、伪造引文、丢观察；独立语义复核检查一条消息中的多项要求。
- 验证：第三轮证据见 `notes/evolution/round-003-20261015-evaluation.md`；修复与新批次结果见 `notes/evolution/round-004-20261015-evaluation.md`。
- 边界：结构覆盖完整不等于语义完整；不能为达到覆盖率而把问题、继续指令和项目事实都升为偏好。

## T02：索引中的旧 JSONL 路径不存在

- 发现：第三轮旧路径大量缺失，但应用的 `read_thread` 仍能返回选定对话的原生消息。没有确定缺失原因。
- 处理：先确认文件确实缺失，再按选定线程分页读取原生用户消息，保留 thread、turn、message ID 和导出哈希。本地生成适配索引供原有提取器使用。
- 验证：第三轮本地 `source-integrity.json` 检查 30 项通过；用户消息未被助手摘要代替。
- 边界：导出文件行号是新导出行号，不能冒充原 rollout 行号；只恢复任务需要的对话，不整库拉取。

## T03：原生读取参数超限或消息被截断

- 发现：当前 `read_thread` 接受 `turnLimit` 最大 10、`maxOutputCharsPerItem` 最大 20000；超限调用返回参数错误。
- 处理：遵守工具当前边界，沿返回 cursor 分页；程序保存原生记录，只向选择阶段返回长度、消息数和完整性。发现正文截断则恢复完整来源或在冻结前换资料。
- 边界：这些是本次工具版本的实测限制，后续以工具当前约束为准。分页完整不代表附件或已经不在源中的内容完整。

## T04：标题看似丰富，用户原话却只有短问句

- 发现：第三轮一条标题提到学习章节，但原话主要是寻找和安装 Skill；26 条直接正文合计仅约 899 tokens。
- 处理：选择时补充不看语义的正文长度与直接消息数量统计；提炼只依据原话。按项目族合并重复任务，不能把两个同项目线程算两份独立支持。
- 边界：字数多也可能只是复制方案或日志。长度改善样本信息量，不能证明存在更多长期偏好。

## T05：用户角色内容不都是独立偏好证据

- 发现：旧批次包含复制的助手计划、IDE 包装及重复表达。
- 处理：提取器区分 `user_authored` 与 `user_plan_confirmation`，移除运行时包装并去重；语义观察继续辨别引用。历史“同意执行”只支持原任务授权。
- 验证：现有 `test-context-evolution-boundaries.py` 覆盖复制方案、包装、重复和来源伪造边界。

## T06：只比较文件大小，会误报实际会话节省

- 发现：候选文件分片后的大小不能说明代理实际读了什么；整表方还可能额外读取 Skill。
- 处理：用 `context-meter.py` 保存每次实际返回的 UTF-8 文本、哈希和 `o200k_base` 数量。分开列共同约束、历史证据、候选读取、额外 Skill；重读重复计数。
- 验证：第三轮 16 个成功 payload 复算通过；候选读取少 62.8%，但不能把 Context 合计差额全部归因于分片。
- 边界：没有包含平台提示、任务提示、工具 Schema、错误消息及主代理整合。需要额外统计才能讨论整个实验成本或延迟。

## T07：脱敏正则可能破坏 JSON 结构

- 发现方式：第三轮代码审查发现先序列化再替换字符串可能吞掉 JSON 引号；这是静态发现的风险，未声称真实私密值泄露。
- 处理：先递归脱敏字符串值，再序列化。用带引号的合成凭据测试有效 JSON，并确认已有 16 份测量 payload 字节不变。
- 边界：凭据模式扫描不是完整隐私判断；个人和敏感主题仍需语义审查。

## T08：Git 连接被旧本机代理阻断

- 发现：历史全局代理端口不可用，当前可用端口不同。
- 处理：本机确认后使用单次命令覆盖，例如 `git -c http.proxy=http://127.0.0.1:7897 fetch origin`，不为本次任务改全局配置；推送后比较本地 HEAD、实时远端 main 和工作区状态。
- 边界：端口是本机当前事实；连接失败时先重新核实，不能永久照搬。不要把凭据写进命令或排障记录。

## T09：控制器命令参数写错

- 发现：使用 `gate --stage verify` 返回参数错误。
- 处理：查 `gate --help`，正确参数为 `gate --for-stage verify`；失败门禁不能被后续命令的成功退出码掩盖。依赖命令应检查返回码后再执行。
- 验证：第三轮最终 verify、report 门禁和 workflow_eval 均通过；上游 Skill 选择可观测性仍为 indeterminate。

## T10：输出预算截断与过度依赖字面匹配

- 发现：合并多个长读取时，工具总输出预算可能截断内容；另一次复核把概括词“图注”当作原话字面词，误报断言失败，原文实际使用了另一种说法。
- 处理：限定文件与片段、给足有依据的输出预算，任何未返回片段不算已读；来源校验使用精确引文，语义覆盖由复核判断，不用固定关键词冒充理解。
- 边界：增大输出上限不是默认全量读取的理由。先缩小读取范围，只有信息不足时扩展。

## T11：多层命令字符串的引号拼接出错

- 发现：第四轮一次只读检查将 JavaScript、PowerShell、Python 字符串嵌套拼接，调用在执行前返回 `SyntaxError`，未运行目标命令。
- 处理：该检查改为直接 `rg` 查询；复杂逻辑保存为脚本，用参数传路径。不要把 JSON 序列化当作 Shell 转义，更不能把未经处理的历史消息插入 Shell 命令。
- 边界：语法错误与命令执行后失败应分别记录；不得因后续命令成功而推定前一步已执行。

## T12：中文在读取工具返回时乱码

- 发现：第四轮隔离回归的首次 bootstrap 未显式启用 Python UTF-8，中文返回乱码；本地 payload 文件仍是正常 UTF-8。该次交付不能算已正确读到核心。
- 处理：`context-meter.py` 固定 stdout 为 UTF-8 和 LF，调用端同时使用 `python -X utf8`。明确重读受影响内容，保留初次失败和重读记录；计量包装先统一 CRLF 为 LF，再原样返回模型。
- 验证：用受控旧编码环境捕获工具实际 stdout 字节，与保存的 UTF-8/LF payload 比较；隔离回归代理重新检查可读性。
- 边界：文件哈希正确不能单独证明终端传输正确。修复后的新批次重新冻结工具版本，不混用乱码尝试或旧结果来报告节省。

## T13：完整旧消息因缺少时间戳而在提炼前消失

- 发现：第四轮原生恢复的旧消息内容完整，但不少 turn 的 startedAt 为 null；原 prepare 仅保留带日期的消息。选定训练的 112 条直接消息中有 76 条受影响。
- 处理：默认 strict 仍排除缺时消息。仅在明确的历史导入中选择 `--message-date-policy thread-bounded`，要求父线程创建与更新时间完整、顺序有效，且整体落在指定窗口；保留消息 timestamp:null 和线程级时间精度标记。已知消息日期仍按原窗口过滤。
- 验证：最小日期策略测试检查默认行为、显式保留、越界/缺失/反转边界拒绝以及已知日期过滤；本轮统计保存于冻结 cohort。
- 边界：父线程日期不能变成用户发言的精确时间。缺少合格边界则失败，不补造日期，也不据此声称精确一周样本。

## T14：缺时消息按时间排序会反转原对话顺序

- 发现：第四轮资格筛选的初版适配器把 null 时间统一当作 0 排序，同值时保留 API 的 newest-first 顺序；因此无日期的旧轮次未恢复时间顺序。
- 处理：按原生分页和轮次顺序恢复 earliest-first，并保留同一轮内部消息顺序；不靠虚构时间来排序。首次 6 个资格导出在任何语义读取或分区冻结前重建，记录适配器版本 2。
- 边界：导出顺序是原生轮次顺序，不代表获得了每条消息的实际发生时间。冻结后发现此问题应建立修订批次，不能悄悄替换已评分来源。

## T15：来源正文的长度包含附件路径和请求包装

- 发现：第四轮提取器标记的 112 条 user_authored 正文合计 4,149 tokens，但其中 7 条仍含文件引用或 Selected text 包装；按明确请求分隔符去掉元数据后为 3,616 tokens，并有 1 条没有请求文字。
- 处理：同时报告字面正文与请求正文的计量口径；观察阶段给空请求、附件引用和转贴内容明确去向，不把路径文字或附件存在当成用户偏好。已冻结的比较输入不回写，以免改变成绩对应的样本。
- 边界：请求分隔符归一化仍不是语义有效信息量；未读取的附件不能凭文件名补全其内容。下次选样本可使用这项补充统计。

## T16：把已安装 Skill 当作仓库内必有的源文件

- 发现：第四轮渐进式臂尝试读取 `skills/engineering-project-workflow/SKILL.md`，仓库中不存在该路径；当前会话的已安装 Skill 列表不等于个人仓库迁入目录。
- 处理：先查仓库 Skill 索引与来源清单。需要运行时版本时，使用会话提供的真实路径并单独记录读取边界；本比较臂未读到该正文，因此没有声称已完成该 Skill 的重叠审查。
- 边界：文件不存在不能推出 Skill 未安装。不要复制一个假文件以便检查通过；失败读取返回的错误也不算成功 Context 正文。

## T17：覆盖校验通过，晋升字段仍可能不合法

- 发现：第四轮渐进式臂的唯一晋升建议使用了 `candidate_audit.related_candidate_ids`，正式校验要求 `related_ids`，因此被拒绝；来源覆盖校验本身已通过。
- 处理：将覆盖检查与完整晋升检查分开。在本地验证夹具中仅更正字段为 `candidate_audit: {"action":"refine","related_ids":["C-20261014-005","C-20261014-013"]}` 后，证据和字段校验通过；原始对照输出保留不改。
- 边界：字段更正不决定是否应该晋升。本次主代理另查现行文档工作流，认为该建议与已有样例风格/版式要求重叠，仍暂缓应用；不能把机械通过写成语义或用户认可。

## T18：结构全覆盖，但问句、范围和具体细节仍未进入观察

- 发现：第四轮两组均通过 112/112 条消息的结构检查；独立模型参考仍指出渐进组 6 项缺失、9 项部分覆盖，全量组 6 项缺失、6 项部分覆盖。
- 原因：无观察分类可以隐藏有任务目的的问句；依赖前文的指令被整体丢弃；概括把“3 题以上”改成“超过 3 题”，丢掉输出栏目或弱化强制约束。部分判断存在解释争议，不能等同于未经记录或程序故障。
- 处理：冻结前逐条复核无观察单元；保留任务意图和未知指代，核对阈值、栏目、强制程度、例外与分工。原始对照保留，另建修订日志并复核已知缺口。具体步骤见 `references/skills/personal-context-observation.md`。
- 边界：历史权限只能记作历史范围；引用方案只能记作分析对象。事后修复不回填两组成绩，也不证明新样本达到 100% 完整。结构检查、语义判断、长期晋升分别报告。

## T19：复核自身的上下文比提炼更大

- 发现：第四轮独立参考、匿名比较和修订复核额外输入 77,643 tokens；仅候选加载变小并不能说明整条流程变省。
- 处理：第五轮先冻结一份观察，风险组和全量组复核同一结果；传完整原文与所连观察，删除重复的长来源编号和无关审计字段。默认检查全部风险消息及固定 20% 的低风险样本；样本发现问题则补查剩余低风险内容，风险包已达全量 80% 则直接全量。
- 验证：路由在旧批次选中 55/112 条消息，覆盖 15 项已知缺口；新批次及合计加载见 `notes/evolution/round-005-20261015-evaluation.md`。补查触发和漏行拒绝有针对性测试。
- 边界：抽查不是完整性证明；新批次没有缺陷也不能证明能识别所有未知缺陷。必须单列本次完整对照的额外成本，保留框架开发与平台输入无法完整计量的边界。

## T20：压缩来源元数据时混淆了项目族与对话

- 发现：第五轮紧凑 Observer 输入保留消息别名和项目族，完整来源映射留本地；准备复核包时发现项目族不能替代父对话边界。
- 处理：在两组复核开始前加入短对话别名，两组格式一致；映射继续指向真实来源。已读取的 Observer 输入及日志不回写，记录这一执行前补充。
- 边界：项目族用于判断证据独立性，对话用于判断上下文归属。短 ID 可以压缩，但这些含义不能一起删除。本轮原文映射与最终观察来源校验通过。

## 新问题的记录方式

每项保留：发现时间与批次、症状、已确认原因/推测、最小修复、验证结果、适用边界、证据路径。未解决写清剩余问题；修复后追加结果，不删除失败记录。公开版只保留去敏机制与命令，本地版保留详细错误和来源。
